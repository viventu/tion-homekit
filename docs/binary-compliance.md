# Проверка бинарного выпуска

Исходники проекта доступны по 0BSD, но это **не** лицензия целой ESP32-прошивки. Arduino-ESP32 3.3.8, ESP-IDF 5.5.4, HomeSpan 2.1.8, криптография и предсобранные библиотеки SoC вносят собственные условия. Для первой публикации GitHub допустим **source-only** репозиторий; до завершения описанной ниже проверки не прикладывать `.bin` как release asset.

## Что известно по текущей сборке

Реестр [прямых зависимостей](../third_party/README.md) фиксирует версии и notices HomeSpan/протокольных данных, но не является SBOM итогового ELF. Предварительный разбор секции `Archive member included` из `.build/homekit/TionHomeKit.ino.map` для `0.2.0-rc3-dev` после чистой macOS-сборки нашёл 79 различных статических архивов и 1163 записи о включённых объектных файлах, включая Arduino core, ESP-IDF, сетевые/криптографические компоненты, runtime компилятора и предсобранные библиотеки SoC. Это консервативная инвентаризация: linker GC может удалить секции позже, а сам map не сообщает лицензии. Установленный пакет `esp32s3-libs` не содержит полного комплекта notices рядом с архивами. Эти числа относятся к dev-сборке и пересчитываются для GM.

## Gate для конкретного GM

1. Сохранить **точно тот** APP/bootloader/partition образ, который прошёл аппаратные испытания, и его SHA-256. Сопоставить с `HEAD^{tree}` публичного снимка, FQBN, версиями toolchain и размерами разделов. Побайтную воспроизводимость в другом каталоге или ОС не предполагать.
2. Из map GM выписать все включённые архивы и объектные файлы, включая compiler runtime, предсобранные SDK-библиотеки и библиотеки Arduino. Для каждого сопоставить пакет, точную версию, upstream source, SPDX-идентификатор и нужный notice. Проверить это по исходникам **той же версии**; один `LICENSE` верхнего уровня ESP-IDF недостаточен для вложенного стороннего кода.
3. Подготовить полный SBOM и комплект notices для реально связанного образа, затем отдельно проверить условия распространения библиотек и доступность требуемых исходников. Официальный `idf.py sbom-create` работает с артефактами сборки ESP-IDF; текущая Arduino CLI сборка не создаёт нужный `project_description.json`, поэтому нельзя выдавать чужой или частичный SBOM за результат этой сборки.
4. Проверить итоговый набор assets по [шаблону заметок](release-notes-template.md). Запретить NVS, полный Flash dump, `.merged.bin`, приватные конфиги и диагностические данные. Для самостоятельной установки описать точные адреса записи и восстановление из [руководства](setup.md). Обычный и диагностический APP маркировать отдельно; HTTP-диагностика открыта без HAP-аутентификации.
5. До публикации draft release убедиться, что хэши assets совпадают с проверенными файлами, все notices приложены, а предупреждения и поддерживаемые версии в заметках актуальны. Если любой пункт не закрыт, публиковать только исходники по tag без бинарных assets.

Первичные источники: [Arduino-ESP32 3.3.8](https://github.com/espressif/arduino-esp32/tree/3.3.8) и его [LICENSE.md](https://github.com/espressif/arduino-esp32/blob/3.3.8/LICENSE.md), [ESP-IDF v5.5.4](https://github.com/espressif/esp-idf/tree/v5.5.4) и [реестр copyrights и лицензий семейства 5.5](https://docs.espressif.com/projects/esp-idf/en/v5.5/esp32/COPYRIGHT.html), [HomeSpan 2.1.8](https://github.com/HomeSpan/HomeSpan/tree/2.1.8), [инструмент ESP-IDF SBOM](https://docs.espressif.com/projects/esp-idf/en/latest/esp32/api-guides/tools/idf-sbom.html). Ссылки на лицензии компонентов требуют повторной проверки для конкретного GM.
