## R1 — P1: чтение статуса может вызвать ложный перезапуск

Место: `libraries/Tion4SCore/src/tion4s/uart_core.cpp`, `UartCore::status`, строки 93–109; вызывающий код — `Esp32UartService::supervise`.

`now_ms` передаётся до захвата блокировки, а `published_ms_` читается под блокировкой. Между этими событиями UART-задача может опубликовать состояние с более поздней меткой времени. Тогда `now_ms - published_ms` переполняется; насыщающее сложение превращает возраст состояния и heartbeat в `UINT32_MAX`. `supervise()` принимает это за остановку UART и перезапускает исправное устройство. Другие потребители статуса получают ложный `fresh=false`.

Детерминированное host-воспроизведение с настоящими `UartCore` и `StallGuard`:

1. Запустить симулятор до получения свежего состояния и heartbeat.
2. Сохранить время вызова `status()` как `t`.
3. Смоделировать вытеснение вызывающей задачи: продвинуть часы на 1 мс и выполнить `core.service()`; он публикует статус времени `t+1`.
4. Продолжить чтение через `core.status(t)` и передать возраст heartbeat в `StallGuard::evaluate`.

Получено под ASan/UBSan: `fresh=0`, `state_age=4294967295`, `heartbeat_age=4294967295`, действие `Restart`. Ожидается свежий статус без перезапуска. Это воспроизводит допустимый порядок выполнения двух задач; ошибка не требует ожидания переполнения `millis()`.

Исправление должно согласовать время измерения с копированием статуса либо корректно обработать публикацию, произошедшую после выборки времени. Нужен regression на это чередование задач и сохранение существующей защиты от настоящего переполнения времени. TSan не обнаруживает такую логическую гонку: доступ к данным защищён.

## R2 — P1: ответ старого опроса может ложно подтвердить выключение нагрева

Место: `libraries/Tion4SCore/src/tion4s/control_transaction.cpp`, `ControlTransaction::observe`, строки 177–181; начало транзакции — `UartCore::start_waiting_command`.

Во время `Reading` первый подходящий `StateResponse` безусловно становится baseline. Запрет новых периодических опросов во время транзакции не учитывает уже отправленный опрос, ответ которого ещё идёт по UART. На `02D0` принимается любой ID; на остальных поддерживаемых версиях все ответы на чтение имеют ID 1, поэтому эта проверка тоже не различает два чтения.

Host-воспроизведение с настоящими `ControlAccess`, `UartCore`, `ControlTransaction` и имеющимся `FakeTion`:

1. Открыть допуск управления, дождаться очередного периодического запроса состояния. В момент этого запроса нагрев выключен.
2. Пока ответ ожидает доставки, включить нагрев штатным управлением симулятора.
3. Через `ControlAccess` отправить «выключить нагрев». Изменение из пункта 2 происходит **до** отправки предчтения новой команды.
4. Доставить ответы в исходном порядке: сначала ответ периодического опроса, затем ответ предчтения.

Получено под ASan/UBSan с задержкой ответа 20 мс, а также 200 мс: `phase=Unchanged`, `writes=0`, фактическое `heater_allowed=1`. После доставки собственного ответа предчтения статус уже показывает включённый нагрев, но результат команды остаётся успешным `Unchanged`. Таким образом, удаление no-op по snapshot не полностью устранило ложное подтверждение. При записи другого поля старый baseline также может вернуть непрошенные поля к прежним значениям.

Нужно согласовать владение всеми запросами состояния, включая незавершённый периодический опрос: старый ответ не должен ни разрешать полную запись, ни завершать новую команду как `Unchanged`. Regression должен проверять этот порядок пакетов для `02D0` и ветки с ID 1. Протокол без уникального ID чтения требует явно описанного порядка ожидания и обработки запоздавших ответов; поведение реального устройства остаётся **NOT RUN**.

## R3 — P2: watchdog обходит предел перезапусков при зависшей UART-задаче

Место: `libraries/Tion4SCore/src/tion4s/esp32_uart_service.cpp`, строки 49–52, 76–89 и 102–105.

Счётчик сохраняется только после `ESP_RST_SW`. При зависании прохода UART прекращаются сбросы task watchdog. Даже если первые три сбоя восстановил `supervise()`, после `GiveUp` зависшая задача остаётся подписанной на watchdog. Его следующий reset имеет причину `ESP_RST_TASK_WDT`; `begin()` обнуляет счётчик, и последовательность перезапусков начинается заново. В read-only варианте закреплённый SDK задаёт timeout 5 с, то есть watchdog может сработать раньше шестисекундного порога `StallGuard` уже при первом зависании.

Подтверждение по исходникам и конфигурации, **без аппаратного воспроизведения**:

- В локальном ESP32-S3 SDK из Arduino-ESP32 3.3.8 включены `CONFIG_ESP_TASK_WDT_INIT=1`, `CONFIG_ESP_TASK_WDT_PANIC=1`, timeout 5 с.
- [HomeSpan 2.1.8, `hsWatchdogTimer::enable`](https://github.com/HomeSpan/HomeSpan/blob/107ffc07f4455754ea89068d8cf2e992de3583e6/src/Utils.cpp) настраивает общий TWDT с `trigger_panic=true`; HomeKit-скетч выбирает 10 с.
- [ESP-IDF 5.5.4, `task_wdt_timeout_abort`](https://github.com/espressif/esp-idf/blob/v5.5.4/components/esp_system/task_wdt/task_wdt.c) устанавливает причину `ESP_RST_TASK_WDT`; [обработка reset reason на ESP32-S3](https://github.com/espressif/esp-idf/blob/v5.5.4/components/esp_system/port/soc/esp32s3/reset_reason.c) сохраняет это отличие от обычного программного reset.

Для ограниченного восстановления нужен общий учёт неуспешных запусков, включая watchdog, и определённый режим после исчерпания попыток. Простого сохранения счётчика при WDT недостаточно: оставленная зависшая задача продолжит инициировать reset. Это требует проверки ESP32-адаптера; текущая host-заглушка его не исполняет.
