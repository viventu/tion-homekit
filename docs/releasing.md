# Подготовка выпуска

Инструкция для сопровождающего. Публичная ветка `main` содержит исходники предварительной версии. Стабильный выпуск и готовые бинарники публикуются после проверок конкретного кандидата и решения сопровождающего.

## Зафиксировать кандидата

1. Укажите версию, публичный commit и tree ID, версии инструментов и FQBN.
2. Соберите обычный и диагностический варианты. Сохраните APP, bootloader, таблицу разделов, размеры и SHA-256 каждого файла.
3. Свяжите аппаратные результаты именно с этими файлами. Новая сборка, даже с прежней строкой версии, не наследует результат автоматически.

Побайтовая воспроизводимость между ОС и каталогами не подтверждена. Проверенный бинарник сохраняют, а не заменяют незаметно повторной сборкой.

## Проверки кода и документации

На чистом checkout выполните:

```sh
scripts/test-host.sh --coverage
scripts/check.sh
git diff --check
python3 scripts/prepare-public-snapshot.py
```

Проверьте обязательные статусы GitHub Actions: GCC, Clang и firmware. Сверьте команды установки, ссылки, совместимость, [историю изменений](../CHANGELOG.md), [границы безопасности](../SECURITY.md) и [сторонние notices](../third_party/README.md).

Проверка снимка ищет частные файлы и ограниченный набор шаблонов. Дополните её ручным просмотром состава, diff и журналов CI, а также специализированным сканером секретов. Порядок переноса исходников без частной истории — в [руководстве публикации](github-publication.md).

## Аппаратные проверки

Пройдите [подготовку оборудования](hardware.md) и [функциональный план](one-visit-test.md). Для обновления нужны резервная копия конкретного стика, рабочий BOOT recovery, совпадающая разметка и проверка сохранности NVS.

На кандидате проверьте обычные команды, сопряжение, синхронизацию с пультом, защитные отказы, ускорение и восстановление. Затем соберите новый длительный журнал; для GM1 принят срок 24 ч на каждом из двух испытательных экземпляров. Журнал другой версии не заменяет этот прогон.

Непроверенные свойства остаются NOT RUN. Если функция исключается из поддерживаемого набора, приведите её доступность и описание в соответствие с этим решением. Текущие открытые проверки — в [сводке](validation.md#открытые-проверки).

## Опубликовать результат

Заполните [заметки о выпуске](release-notes-template.md): изменения, проверенное оборудование, ограничения, установка и восстановление. Создайте tag нужного публичного commit и draft release, сверяйте его с проверенным кандидатом.

Исходники можно выпускать отдельно. Для `.bin` и `.elf` сначала завершите [проверку состава и лицензий бинарника](binary-compliance.md). NVS, полные Flash-образы, `.merged.bin`, коды сопряжения и диагностические журналы в assets не включаются.

Перед публикацией проверьте хэши, ссылки и комплект notices. Обычный и диагностический варианты должны быть различимы; открытый HTTP-интерфейс диагностического образа указывается явно. CI ничего не записывает на устройства и не выполняет OTA.
