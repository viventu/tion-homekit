# Условия публичного выпуска

Лицензия собственного кода выбрана владельцем: [0BSD](../LICENSE). 2026-09-26 владелец разрешил публикацию исходников кандидата в [viventu/tion-homekit](https://github.com/viventu/tion-homekit) после проверки снимка и GitHub Actions. Выпуск испытанного GM и распространение бинарников остаются отдельными действиями после завершения соответствующих проверок. Сейчас исходники — кандидат `0.2.0-gm1`, оба устройства — `0.2.0-gm1-diag`; базовые проверки PASS, отдельные суточные прогоны IN PROGRESS. Наличие удачной сборки или продолжающегося soak не означает готовность к релизу.

## Исходники и история

1. Проверить финальный текст `LICENSE` (0BSD) и соответствие публичного имени `tion-homekit` личному аккаунту владельца. Исходная лицензия не покрывает сторонние компоненты и не означает, что выпуск уже разрешён.
2. Проверить все экспортируемые Git refs, теги и файлы на credentials, NVS, частные конфиги и постоянные идентификаторы. Аудит 2026-09-24 проверил 253 доступных на тот момент исторических blob по шаблонам: секреты и бинарные дампы не обнаружены, полные MAC/hostname найдены в документах. Это ограниченная проверка, а не гарантия отсутствия любых секретов.
3. Прежние коммиты сохраняют аппаратные идентификаторы. Владелец выбрал [чистый снимок GM](github-publication.md) без истории разработки. Исходная история не переписывается и не добавляется как remote публичного репозитория. `.private/`, `.arduino/`, `.build/` не входят в снимок; Git ignore сам по себе не защищает от `git add -f`.
4. После создания публичного репозитория включить GitHub Private Vulnerability Reporting и проверить кнопку отправки приватного отчёта; до этого `SECURITY.md` не обещает рабочего канала. Проверить относительные ссылки, quickstart и [реестр сторонних компонентов](../third_party/README.md).
5. Проверить снимок скриптом `scripts/prepare-public-snapshot.py`, вручную просмотреть экспортируемый состав и получить первый зелёный GitHub Actions до открытия доступа. Порядок — в [плане публикации](github-publication.md).

## Проверки кандидата

1. Пройти `scripts/test-host.sh`, `git diff --check` и `scripts/check.sh` на чистом checkout. Чистая установка toolchain и полный check прошли на macOS arm64 2026-09-24; первый Linux/GitHub Actions запуск остаётся NOT RUN и проверяется после создания площадки.
2. Присвоить версию конкретному кандидату и записать commit, FQBN, toolchain, размеры и SHA-256 bootloader/partition/APP. Dev-сборки не выдавать за уже испытанный `rc2`. Независимая воспроизводимость бинарников пока не установлена.
3. Для каждого стика провести [preflight](hardware.md), подтвердить собственную проверенную резервную копию, ROM BOOT и соответствие разделов. Обновлять только после закрытия аппаратных условий; проверить APP и NVS до/после. Полное восстановление заводской копии в реальном опыте ещё NOT RUN.
4. На новом кандидате повторить пересекающиеся команды, два последовательных защитных отказа и новую команду без rearm, предел срока boost, ручную отмену и восстановление после reboot/потери связи. NVS fault injection выполняется на host; повреждать рабочую NVS устройства ради испытания не требуется.
5. Подтвердить обе независимые identity, HAP database/Apple UI, устойчивость UART/питания при сетевых сбоях и provisioning, затем отдельный 24-часовой прогон нового образа на обоих устройствах (решение владельца 2026-09-26, см. [GM1](gm1-validation.md)). Существующий `rc2` soak — данные о прежнем образе; во время него были подтверждённые действия владельца через HomeKit. Монитор сам UART-команд не посылает.
6. Закрыть или явно ограничить неподтверждённые свойства: электрические уровни/ревизии, отрицательные температуры и датчик выхода, длительная терморегуляция, реальный сброс фильтра только после замены. Для выключенного из подтверждённого набора свойства изменить публичное описание и доступность, а не отмечать фиктивный PASS.

## Бинарные артефакты

Выпуск `.bin` требует полного SBOM реально связанных SDK/библиотек, комплектов notices и проверки условий каждой лицензии; порядок и текущие пробелы описаны в [проверке бинарного выпуска](binary-compliance.md). Текущая таблица прямых зависимостей неполна для бинарного распространения. В релиз никогда не включают NVS, полный Flash dump или provisioning credentials. Диагностический и обычный образы явно различают; открытая HTTP-диагностика описывается в release notes. Никакой OTA или записи на устройство CI не выполняет.
