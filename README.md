# Tion 4S → HomeKit

Прямая интеграция Tion Family 4S с HomeKit через Wi-Fi. Один LilyGO T-Dongle S3 обслуживает один бризер; Raspberry Pi не участвует в рабочем пути. Это DIY-аксессуар, не сертифицированный Apple и не официальный продукт Tion. Собственный код проекта доступен по [0BSD](LICENSE); условия сторонних компонентов перечислены в [реестре](third_party/README.md).

**Статус устройств: оба стика работают на `0.2.0-gm1-diag` и проходят отдельные 24-часовые прогоны. На обоих подтверждены сохранность NVS и сопряжения, свежий UART, исчезновение переключателя допуска и обычные команды питания/скорости через HomeKit.** На первом стике ещё с `rc1` испытаны питание, все шесть скоростей, рециркуляция, звук, подсветка, нагрев с уставкой и локальное пятиминутное ускорение. Второй стик с `rc2` подтвердил отдельные Wi-Fi/HomeKit credentials, чтение UART, включение, рециркуляцию, звук, подсветку и автоматическое завершение пятиминутного ускорения. Температуры и предупреждение фильтра видны в «Доме»; опасный сброс при работающем первом бризере отклонён до UART-записи. Настоящий сброс после замены фильтра не выполнялся. С обоих ESP32-S3 сняты независимые локальные резервные копии 16 МБ; обновление первого APP до `rc2` сохранило NVS и сопряжение.

**Статус исходников: кандидат GM `0.2.0-gm1`; базовый старт на обоих стиках — PASS, итог суточного прогона — IN PROGRESS.** Аудит исправил пересечение HomeKit-команд, повторное закрытие допуска после отказа, срок ожидания в очереди и обработку ошибок сохранения pairing verifier. Ревью 2026-09-25 добавило ожидание однотипной команды, исход `Unchanged`, безопасное выключение при ошибках устройства, восстановление кадров парсером, watchdog с ограниченным перезапуском и отрицательные температуры; подробности — в [истории изменений](CHANGELOG.md). Оба APP обновлены с `rc2-diag`; установка и начало наблюдения записаны в [журнале GM1](docs/gm1-validation.md). Прежние мониторы `rc2` остановлены, их журналы сохранены отдельно. См. [отчёт аудита](docs/audit-2026-09-24.md), [условия выпуска](docs/releasing.md) и [план публикации на GitHub](docs/github-publication.md).

`firmware/TionReadOnly` остаётся транспортным образом без записи. Новый `firmware/TionHomeKit` добавляет Fan, нагрев, температуры, рециркуляцию, пятиминутное ускорение, звук, подсветку и фильтр. В GM1 управление доступно сразу после получения свежего состояния поддерживаемого устройства. Переключатель «Разрешить управление» и 30-минутный срок удалены по решению владельца; сопряжение HomeKit и протокольные защиты сохраняются. После ошибки следующая явная команда разрешена, автоматического повтора не происходит. Каждая команда использует свежее чтение, одну запись и проверку результата; повторной записи по таймауту нет. Полный контракт остаётся Draft до проверки защитных сценариев и нового кандидата на `02D0`. Один стик обслуживает один бризер, Wi-Fi и HomeKit identity хранятся в разных NVS; код сопряжения задаётся при начальной настройке и не публикуется.

`scripts/check.sh` запускает host-тесты, compile-only spike и обе сборки. `rc2` исправляет граничный случай таймера ускорения у конца 30-минутного допуска; этот образ использовался на обоих стиках до обновления GM1. Подробные результаты и ограничения `02D0` — в [журнале](docs/validation.md). Температуры публикуются в диапазоне −50…100 °C; отображение отрицательных значений в «Доме» ещё не проверено, сырое значение всегда есть в диагностике. Сброс фильтра доступен отдельной кнопкой после замены фильтра и только при выключенном бризере и запрете нагрева; его подтверждение по ресурсу ещё не испытано. На свежем сопряжении Apple «Дом» может дать трём вспомогательным переключателям типовые имена; на втором устройстве их сопоставили по UART и переименовали в настройках «Дома».

Предлагаемый стек: HomeSpan 2.1.8, Arduino-ESP32 3.3.8 (ESP-IDF 5.5.4), Arduino CLI 1.5.1 и узкая адаптация UART-протокола из `dentra/esphome-tion`. Это кандидат, а не утверждённая production-архитектура. См. [установку и восстановление](docs/setup.md), [доказательства](docs/evidence.md), [контракт](docs/spec.md), [архитектуру](docs/architecture.md), [аппаратный preflight](docs/hardware.md), [план единого аппаратного прогона](docs/one-visit-test.md) и [результаты проверок](docs/validation.md).

После исправлений независимого [ревью](docs/review-2026-09-26.md) предчтение команды ждёт ответы на прежние запросы. Если ответ потерян, чтение состояния продолжается, но запись блокируется до получения всех ожидаемых ответов или перезапуска стика. Три последовательных программных/watchdog-сбоя переводят следующий старт в безопасный режим без UART и HomeKit, с красным светодиодом; повторный запуск допускается после отключения и подачи питания. Аппаратная проверка этих сценариев — **NOT RUN**.

По решению владельца на оба стика установлен `0.2.0-gm1-diag` с сохранением их NVS; идёт сбор **24 часов новых логов**. Это кандидат GM до завершения проверки; старый журнал не заменяет этот прогон. План, хэши и результаты — в [журнале GM1](docs/gm1-validation.md).

## Проверка компиляции без устройства

Для host-тестов нужны Git, Bash, Python 3.9+ и Clang либо GCC с AddressSanitizer, UndefinedBehaviorSanitizer и ThreadSanitizer. Скрипт сам выбирает компилятор, у которого эти runtime действительно линкуются (`CXX` задаёт его явно), собирает тесты параллельно и пишет `.build/host/compile_commands.json` для `clang-tidy` и clangd:

```sh
scripts/test-host.sh
```

Host-сборка проверяет оба скетча и настоящий `Esp32UartService`, включая его задачу, блокировки и восстановление. Сквозные сценарии проходят путь HomeKit → `ControlAccess` → UART-задача → драйвер → симулятор бризера и обратно; на границе ESP-IDF/FreeRTOS стоят управляемые заглушки. Отдельный набор проверяет HomeKit с более простой заглушкой адаптера. Ключ `--coverage` требует 100 % строк и ветвей всего C++-кода в `libraries/Tion4SCore/src` и `firmware`, без исключения ESP32-адаптера. GCC использует `gcov` 9+, Clang — соответствующие `llvm-profdata` и `llvm-cov` (на macOS находятся через `xcrun`). Linux/GCC проверяется в CI:

```sh
scripts/test-host.sh --coverage
```

Для сборки прошивки нужны Arduino CLI 1.5.1, Arduino-ESP32 3.3.8 и чистый checkout HomeSpan 2.1.8 на закреплённом commit. Установщик поддерживает macOS/Linux на arm64/x86_64, проверяет SHA-256 архива CLI и создаёт изолированное окружение; каталог назначения должен отсутствовать. Нужны интернет, `curl`, `tar`, Git и несколько ГБ свободного места. На Apple Silicon для нативного ctags также нужны `make` и Command Line Tools.

```sh
scripts/install-toolchain.sh
export ARDUINO_CLI="$PWD/.arduino/bin/arduino-cli"
export ARDUINO_CLI_CONFIG="$PWD/.arduino/arduino-cli.yaml"
export HOMESPAN_LIBRARY_DIR="$PWD/.arduino/libraries"
scripts/check.sh
```

Можно задать новый каталог через `TION_TOOLCHAIN_DIR`; после установки укажите его в трёх переменных выше. Повторная установка поверх существующего окружения запрещена. Для уже установленного toolchain достаточно настроить эти переменные. Изменённые или дополнительные файлы HomeSpan отклоняются, даже если HEAD соответствует закреплённому commit.

На arm64 macOS установщик при необходимости собирает Arduino ctags 5.8-arduino11 нативно и сохраняет исходный бинарник. Отдельный запуск: `ARDUINO_CLI_DATA_DIR="$PWD/.arduino/data" scripts/fix-arduino-ctags-arm64.sh`. Закреплённый commit и границы воспроизводимости перечислены в [реестре зависимостей](third_party/README.md). GitHub Actions выполняет те же host/compile проверки. Текущие результаты доступны в [Actions](https://github.com/viventu/tion-homekit/actions/workflows/check.yml); первый облачный прогон проверяется при публикации исходников.

Пакет `esp32:esp32` скачивает инструменты и для других чипов, хотя целевая плата — S3. `scripts/check.sh` вызывает только `arduino-cli compile`, без загрузки прошивки; он также проверяет диагностическую сборку HomeKit. Её можно отдельно собрать с `TION_DIAGNOSTICS=1 scripts/build-homekit.sh`. Она добавляет локальную страницу `/tion-status` через WebLog HomeSpan с временем работы, доступной памятью, запасом стека UART-задачи, счётчиком перезапусков по паузе heartbeat, числом ответов и возрастом состояния, паузами heartbeat, ошибками UART и последним декодированным состоянием. Температура `Raw current` не объявляется комнатной. Страница доступна по HTTP без HAP-аутентификации и предназначена для испытаний только в доверенной домашней сети. Результат текущего запуска записан в `docs/validation.md`.

Перед подключением к Tion нужно подтвердить ревизии стиков, PSRAM, версии прошивок Tion, электрический интерфейс, восстановление через BOOT и фактический дедлайн обязательного обмена. Порядок проверки — в [аппаратном preflight](docs/hardware.md).

Для длительного чтения уже установленного диагностического образа на macOS можно запустить `caffeinate -i python3 scripts/monitor-diagnostics.py --url http://tion-4s-XXXXXX.local/tion-status --output .private/soak/tion-8h.csv --hours 8 --interval 60`, заменив `xxxx` адресом своего стика. Скрипт записывает только выбранные поля статуса в CSV с правами `0600`, не посылает UART-команд и не перезаписывает готовый файл. Mac должен оставаться включённым и подключённым к домашней сети. Перезапуск ESP распознаётся по счётчикам и строке Reset Reason; отсутствие сети фиксируется отдельной строкой с ошибкой.

После длительного прогона `python3 scripts/review-soak.py .private/soak/tion-8h.csv --expected-hours 8` выведет сводку. Код завершения `0` означает, что длительность и автоматические пороги пройдены; `1` — обнаружена проблема; `2` — прогон ещё не набрал заданную длительность. Проверяются доступность, свежесть UART-состояния, разрыв heartbeat, перезапуски, HomeKit/Wi-Fi, ошибки и минимум свободной памяти. Автоматический результат дополняется разбором аппаратного журнала перед релизным решением.

## English summary

Direct HomeKit integration for the Tion Family 4S breezer: one LilyGO T-Dongle S3 (ESP32-S3) per breezer speaks the breezer's UART protocol and exposes it through [HomeSpan](https://github.com/HomeSpan/HomeSpan); no bridge, cloud or ESPHome runtime is involved. It is a DIY accessory, not certified by Apple and not an official Tion product. GM1 makes control available to paired users once a supported device has fresh state; every command uses a fresh read, one write and a verification read. Earlier firmware was tested on two breezers with firmware `02D0`. Both sticks run candidate `0.2.0-gm1-diag`, have passed startup and basic HomeKit checks with pairing preserved, and are under separate new 24-hour observations. The GM1 observations have not completed. Project documents are in Russian; code identifiers and comments are in English. Run `scripts/test-host.sh` for host tests and see the commands above for firmware builds. Own code is [0BSD](LICENSE); third-party terms are listed in [third_party/README.md](third_party/README.md).
