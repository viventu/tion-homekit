# Участие в проекте

Исправления, тесты и улучшения документации принимаются через pull request в [viventu/tion-homekit](https://github.com/viventu/tion-homekit). Для крупного изменения сначала откройте [issue](https://github.com/viventu/tion-homekit/issues), чтобы обсудить задачу и совместимость.

Документы проекта пишем по-русски, идентификаторы и комментарии в коде — по-английски. Собственный код распространяется по [0BSD](LICENSE). Присылая изменение, вы предоставляете его на тех же условиях и подтверждаете право это сделать. Для заимствований сохраняйте исходную лицензию и уведомления в [third_party](third_party/README.md).

## Подготовка изменения

1. Создайте ветку от актуальной `main`. Ограничьте PR одной задачей и опишите наблюдаемую проблему.
2. Сверьтесь с [архитектурой](docs/architecture.md) и [контрактом устройства](docs/spec.md). Переносимое ядро находится в `libraries/Tion4SCore`, интеграция HomeKit — в `firmware/TionHomeKit`.
3. Добавьте проверку изменённого поведения. Для UART нужны эталонные или синтетические кадры и сценарии отказа; для HAP — проверка IID, сопряжения и миграции схемы. Новые выводы о протоколе сопровождайте версией первичного источника в [реестре](docs/evidence.md).
4. Укажите в PR выполненные проверки, их границы и способ восстановления, если затронуты прошивка или сохранённые настройки.

## Проверки перед PR

Для изменений C++ выполните:

```sh
scripts/test-host.sh --coverage
git diff --check
```

Для изменений прошивки и сборки дополнительно выполните `scripts/check.sh` с [закреплённым окружением](README.md#установка). Для правок только документации локально достаточно проверить ссылки, команды и `git diff --check`; обязательные проверки GitHub Actions всё равно должны пройти перед слиянием.

Порог покрытия — **100% строк и ветвей всего производственного C++** в `libraries/Tion4SCore/src` и `firmware`, включая ESP32-адаптер и оба скетча. Заглушки платформы и сторонние библиотеки в эту метрику не входят. Не исключайте защитные ветви ради прохождения порога. Подробности интеграционных тестов, санитайзеров и отчётов — в [руководстве по тестированию](docs/testing.md).

Используйте `CHECK` из `tests/support/check.h` и стиль `.clang-format`. Не смешивайте массовое форматирование с изменением логики. Аппаратные результаты обозначайте PASS, FAIL или NOT RUN для конкретной версии; успешный тест на компьютере не заменяет проверку на ESP32.

## Данные и оборудование

Не прикладывайте пароли, коды сопряжения, NVS, полные образы Flash, необработанную страницу диагностики или идентификаторы домашней сети. Для отчёта достаточно версий, обезличенного сценария и выбранных метрик. Каталоги `.private/`, `.arduino/` и `.build/` не входят в Git.

Аппаратные испытания выполняются по [плану проверок](docs/one-visit-test.md) после [подготовки оборудования](docs/hardware.md). Fuzzing на реальном бризере, изменение eFuse и прошивки контроллера Tion не входят в тестовый процесс проекта.

Выпуски готовятся по [инструкции сопровождающего](docs/releasing.md). Правила общения — в [CODE_OF_CONDUCT.md](CODE_OF_CONDUCT.md).
